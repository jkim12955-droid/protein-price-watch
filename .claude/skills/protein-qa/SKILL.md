# protein-qa

참가격 가격 데이터와 식약처 영양 데이터를 이어 붙인 결과가 믿을 만한지 열 가지를 코드로 점검한다. 사람이 눈으로 훑는 대신 매번 같은 기준으로 같은 표를 찍는다.

## 언제 쓰나

- `python pw.py load` 다음, `python pw.py report` 전. 파이프라인 안에서는 자동으로 이 순서로 돈다.
- 리포트 숫자가 이상해 보일 때. 먼저 이 점검표를 본다.
- 임계값을 바꾸고 싶을 때. `config/qa_thresholds.json` 을 고치고 다시 돌린다.

## 실행

```
python pw.py qa
```

표준 출력에 마크다운 표가 찍히고, 같은 내용이 `docs/qa/YYYY-MM-DD_qa.md` 와 `data/qa_latest.json` 에 남는다. 리포트는 `qa_latest.json` 을 읽어 5절에 붙인다.

종료 코드는 둘이다. 0 이면 정상 또는 주의, 1 이면 실패 항목이 하나라도 있다. GitHub Actions 는 1 을 받으면 그 실행을 실패로 표시하고 저장소 주인에게 이메일을 보낸다.

## 점검 항목

| 항목 | 무엇을 보나 | 정상 휴장과 실패를 어떻게 가르나 |
|---|---|---|
| 조사 공백 | 마지막 조사일로부터 며칠 지났나 | 조사가 격주 금요일이라 14일까지는 정상. 16일 넘으면 주의, 24일 넘으면 실패. 8월 7일과 28일 사이가 실제로 3주 비었으므로 21일 정도는 조사 쪽 사정으로 보고 주의에서 멈춘다 |
| 수집 건수 | 최신 조사분 행 수 | 이전 조사 중앙값의 70% 아래면 주의, 30% 아래면 실패. 0건이면 실패 |
| 원본 대조 | API 가 준 건수와 DB 행 수 | 다르면 실패. A04 가 이걸 안 해서 빈 날짜를 몇 달 몰랐다 |
| 원본 중복 | 같은 조사일·판매점·상품이 두 번 온 수 | 있으면 주의. 적재는 마지막 값을 쓴다 |
| 상품 커버리지 | 가격이 하나라도 있는 식품 비율 | 90% 아래면 주의 |
| 매칭률 | 단백질 순위 대상 소분류의 상품 중 영양 항목이 붙은 비율(사람이 뺀 것은 분모에서 제외) | 60% 아래 주의, 40% 아래 실패 |
| 가격 급변 | 이전 조사 대비 중앙값이 2배 넘거나 반값 아래인 상품 | 전체의 5% 넘으면 주의. 단위나 상품 정의가 바뀐 신호 |
| 단위 상식 | 계란 개당 무게가 40~75g 인가, 무게 환산이 안 되는 식품이 있나 | 벗어나면 주의. 원본 총량 오류를 잡는다 |
| 기준선 입력 | 하림 훈제 닭가슴살 가격·용량이 들어 있나 | 없으면 주의. 비교 절이 비게 된다 |
| API 호출 | 이번 실행에 가격 API 를 몇 번 불렀나 | 1,800 넘으면 주의. 하루 한도가 2,000 이다 |

## 판정을 읽는 법

- 정상: 아무것도 안 해도 된다.
- 주의: 리포트는 나온다. 표의 설명을 읽고 원인이 데이터 쪽인지 코드 쪽인지 본다.
- 실패: 리포트를 만들지 않는다. 먼저 `data/_run_*.log` 와 `data/raw/<날짜>/meta.json` 을 보고, 수집 문제면 `python pw.py collect --date YYYYMMDD --force` 로 그 날짜만 다시 받는다.

## 항목을 더하는 법

`pipeline/qa.py` 에 `check_이름(con, th, ...)` 함수를 하나 더 쓰고 `run()` 의 목록에 넣는다. 함수는 name, status(ok/warn/fail), value, threshold, message 다섯 키를 가진 dict 를 돌려주면 된다. 임계값은 `config/qa_thresholds.json` 에 두고 `_왜` 키에 그 숫자를 고른 이유를 적는다.

## 이 스킬이 빌린 것

점검을 독립된 함수로 쪼갠 구성은 A15(읽기 전용 데이터 품질 MCP)에서, 정상·주의·정지 세 단계 판정과 임계값을 숫자로 못 박는 방식은 A06(AI Analyst 검증 게이트)에서 가져왔다.
