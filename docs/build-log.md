## 2026-09-10 (목) 4단계 준비, 무게 환산과 데이터 이상치

100g당 가격을 내려면 상품 한 묶음이 몇 그램인지 알아야 한다. pipeline/quantity.py 가 세 단계로 구한다. 무게·부피 단위면 총량을 그대로 쓰고, 개수 단위면 detailMean 의 "120g*5개입" 이나 "대란(52g~59g)" 을 읽고, 그것도 없으면 상품명의 "(300~500g)" 범위 중간값을 쓴다. 식품 457개 중 454개가 환산됐다. 못 한 셋은 애호박, 양배추, 오이라 단백질과 무관하다.

CJ 1등급 깨끗한 계란 15개짜리는 설명이 비어 있어서 개당 52g 을 곱했다. 같은 회사의 10개짜리가 520g 으로 적혀 있어 거기서 가져온 값이다. 이건 내가 정한 가정이라 코드에 출처를 적었다.

이상치를 하나 찾았다. 청정원 자유방목 동물복지 유정란 10개짜리의 총량이 780g 이다. 개당 78g 인데 대란은 52g 에서 60g 이다. 같은 회사 15개짜리 값을 그대로 옮긴 것으로 보인다. 원본을 고치지 않고 그대로 두되, 품질 점검에 "계란 개당 무게가 40g 에서 75g 을 벗어나면 표시" 항목을 넣기로 했다. 원본 데이터의 오류를 코드가 잡아내는 첫 사례다.

영양 API 에서 원재료를 찾는 방법도 정리됐다. R1 그룹은 "돼지고기_삼겹살(삼겹살)_생것", "소고기_한우_등심_생것" 처럼 이름을 짓는다. 참가격은 쇠고기라고 쓰고 영양 DB 는 소고기라고 써서 그대로는 안 맞는다. 신선식품 축산·수산 18개는 이름 규칙이 제각각이라 자동 매칭 대신 사람이 한 번 짝을 지어 표로 두기로 했다. 가공식품은 브랜드 상품명을 그대로 넣으면 P 그룹에서 정확히 잡히는 경우가 있어 자동 매칭을 시도한다. 그 성공률이 얼마인지는 다음 절에 적는다.

## 2026-09-10 (목) 4단계, 매칭 첫 실행이 깨진 기록

상품 457개에 영양 항목을 잇는 매칭을 처음 돌렸다. 20분쯤 지나 영양 API 가 한 검색어에 "System Error!!" 를 돌려줬고, 코드가 그것을 치명적 오류로 다뤄 전체 실행이 멈췄다. 검색 결과 캐시를 끝에 한 번만 저장하게 해둔 탓에 그때까지 부른 호출이 전부 사라졌다. 결과 표도 한 트랜잭션으로 묶어 둬서 한 건도 남지 않았다.

A04 의 교훈을 그대로 겪었다. 한 상품의 실패로 전체를 버리지 말 것. 세 가지를 고쳤다. 영양 API 일시 오류는 간격을 두고 세 번 다시 묻고, 그래도 안 되면 그 상품만 미매칭으로 남기고 실패한 검색어를 따로 적는다. 캐시는 50건마다 저장한다. 매칭 결과는 상품 하나마다 바로 커밋해서, 중단되면 다음 실행이 안 한 것부터 이어서 한다.

깨진 실행에서 하나 더 배운 것. 명령 끝에 `| tail` 을 붙여 두면 파이썬이 죽어도 종료 코드가 0 으로 나온다. 로그는 파일로 받고 종료 코드는 따로 적기로 했다.

## 2026-09-10 (목) 4단계, 매칭과 점검이 실제로 돈 기록

매칭을 다시 돌려 끝까지 갔다. 식품 457개에 시도해 영양 API 를 725회 불렀고 검색 캐시가 남아 그 뒤로는 호출 없이 다시 돌 수 있다.

첫 순위표가 설계의 구멍을 두 개 드러냈다. 칠성사이다 제로가 단백질 19.9g 으로 1위였다. 부분 매칭이 "제로초코볼"을 골라 준 것이다. 그 아래로 밀가루가 줄줄이 있었다. 이건 매칭이 틀린 게 아니다. 밀가루는 100g 에 단백질 10g 이 들어 있고 100g 에 150원이라 단백질 1g 이 15원이다. 숫자로는 가장 싼 단백질이지만 아무도 밀가루를 단백질원으로 먹지 않는다. 워크북 A-3 에 적어 둔 "조미료처럼 단백질 비율은 높지만 그대로 먹지 않는 것은 내가 걸러낸다"가 바로 이 자리였다.

두 가지를 고쳤다. 소분류 규칙을 허용 목록으로 바꿔, 계란·육류·수산·두부·유제품·육가공·수산가공·프로틴·두유·만두·견과·너겟·돈까스 27개 소분류만 순위 대상으로 뒀다. 나머지는 계산은 하되 순위에 올리지 않고 "숫자만 보면 더 싼 것도 있다"는 한 줄로 리포트에 남긴다. 그리고 부분 매칭은 규칙이 있는 소분류에서만, 단어가 75% 이상 겹칠 때만 받는다.

그래도 남양 맛있는우유GT 가 단백질 6g 짜리에, 셀렉스 웨이프로틴 음료가 60g 짜리 파우더에, 서울우유 흰우유가 아이스크림 "흰우유콘"에 이어져 있었다. 분류별로 단백질 상식 범위를 두어 벗어나면 후보를 버리게 했다. 우유는 100g 에 2.5g 에서 4.5g, 프로틴 음료는 3g 에서 15g, 계란은 10g 에서 15g 이다. 이 범위는 config/categories.json 에 있고 사람이 정한 짝에는 적용하지 않는다.

매칭률의 분모도 고쳤다. 처음엔 식품 전체를 분모로 세서 36% 가 나와 점검이 실패했다. 과자와 음료까지 세고 있었던 것이다. 순위 대상 소분류의 상품 108개 중 사람이 뺀 10개를 제외한 98개를 분모로 하니 83개가 붙어 85% 다. 무엇을 분모로 삼느냐가 지표의 뜻을 바꾼다는 걸 숫자로 봤다.

점검 결과는 주의 두 건에 실패 없음이다. 주의는 기준선 미입력과 계란 개당 78g 이상치다. 가격 급변 항목은 8월 7일 대비 4개를 잡았다. 덴마크 우유가 1,300원에서 2,980원으로 2.3배, 오뚜기 치킨너겟이 9,980원에서 3,990원으로 0.4배다. 전체의 0.7% 라 주의 기준 5% 안이지만 리포트에 이름이 찍힌다.

## 2026-09-10 (목) 6단계 준비, 공개 직전 점검에서 나온 것들

원격 저장소를 만들기 전에 저장소를 다섯 갈래로 점검했다. 유출, 액션 워크플로, 문서와 코드의 불일치, 남의 컴퓨터에서의 재현성, 데이터를 공개해도 되는지. 지적마다 세 번씩 반박을 시도해 살아남은 것만 고쳤다. 공개하고 나면 되돌리는 값이 훨씬 비싸서 순서를 이렇게 잡았다.

세 가지가 공개를 막을 만한 것이었다.

첫째는 인증키가 새는 경로였다. `api.py` 가 요청이 실패하면 URL 앞 120자를 예외 메시지에 담는데, 그 안에 `serviceKey=` 가 들어간다. `collect.py` 는 상품 하나가 실패하면 그 메시지를 `meta.json` 에 적고, 워크플로는 `meta.json` 을 저장소에 커밋한다. 지금까지 실패한 상품이 없어 아직 새지는 않았지만, 상품 604개를 도는 동안 한 번만 흔들려도 키의 3분의 1이 공개 저장소에 영구히 박히는 구조였다. 더 나쁜 건 액션 로그다. URL 에 실리는 키는 인코딩을 거쳐 원래 문자열과 달라지므로 GitHub 이 자동으로 가려주는 마스킹에 걸리지 않는다. `serviceKey` 값을 지우는 함수를 만들어 예외 메시지와 경고 출력이 모두 그것을 거치게 했다.

둘째는 워크플로에 매칭 단계가 없다는 것이었다. 로컬에서는 손으로 `match` 를 돌리고 나서 `qa` 를 돌렸으니 멀쩡했는데, 워크플로는 수집·적재 다음에 바로 점검으로 넘어간다. 새로 클론한 환경에는 매칭 결과가 없으니 예약 실행은 매번 점검에서 죽었을 것이다. "사람이 손대지 않아도 돈다" 고 적어둔 문장이 실제로는 한 번도 성립한 적이 없었다. 단계를 넣었고, 캐시가 있어 새 상품이 없으면 영양 API 호출이 0회로 끝나는 것도 확인했다.

셋째는 매칭 표의 정의가 `match.py` 안에만 있다는 것이었다. 저장소를 새로 받아 매칭을 건너뛰고 점검이나 리포트를 돌리면 표가 없다며 트레이스백으로 죽는다. 표 정의를 적재 쪽으로 옮겨 매칭을 안 돌려도 "매칭 0건" 으로 정직하게 보이게 했다. 같은 자리에서 리포트도 고쳤다. 매칭이 비면 순위가 빈 리포트가 만들어져 멀쩡하던 지난 리포트를 덮어썼다. 이제는 쓰지 않고 멈춘다.

나머지 중에 기억에 남는 것 둘.

수동 실행 입력값을 셸에 그대로 넣고 있었다. 시크릿 세 개가 환경변수에 올라간 상태에서 임의 명령을 실행할 수 있는 통로다. 환경변수로 건네 셸이 해석하지 못하게 했다.

점검표 파일 이름을 실행일로 지었더니, 조사는 격주인데 파일은 매일 하나씩 생긴다. 1년이면 거의 같은 내용의 마크다운 365장이 쌓이고 봇 커밋 365개가 사람 커밋을 덮는다. 커밋 히스토리 자체를 무인 운영의 증거로 내세우는 프로젝트에서 그 증거가 스스로 읽을 수 없게 되는 셈이다. 이름을 조사일 기준으로 바꾸니 매일 돌아도 같은 파일에 덮어써서 한 해 26장이 된다. 리포트 파일 이름도 같은 이유로 조사일 주차로 바꿨다. 실행한 날이 아니라 조사한 날이 기준이어야 다시 돌려도 같은 자리에 쓴다.

인증서 검증 우회도 손봤다. 맥에서 인증서를 못 찾는 문제 때문에 넣어둔 우회가 CI 에서도 그대로 살아 있었다. 조용히 검증을 끄면 중간에 누가 끼어들어도 모른다. CI 에서는 켜지지 않게 막았다.

고치고 나서 처음부터 다시 돌렸다. 적재 대조 두 조사일 모두 일치, 매칭 83/98, 점검 실패 0, 리포트 순위 67개. 부침두부를 손으로 다시 계산해 1,480원 ÷ (300g ÷ 100 × 8.0g) = 61.7원, 리포트와 같았다.

## 2026-09-10 (목) 6단계, 첫 자동 실행이 깨진 기록

원격 저장소를 만들고 시크릿을 넣고 첫 실행을 눌렀다. 수집 단계에서 죽었다.

```
RuntimeError: GET 실패(3회): https://apis.data.go.kr/.../getProductPriceInfoSvc?serviceKey=***&...
:: <urlopen error timed out>
```

먼저 확인한 것은 고친 마스킹이 실제로 작동했다는 것이다. 공개 저장소의 실행 로그에 키가 아니라 `serviceKey=***` 가 찍혔다. 몇 시간 전에 고치지 않았다면 지금 인증키 앞부분이 공개 로그에 박혀 있었을 것이다.

원인은 세 번을 좁혀서 찾았다.

첫 번째 가설은 참가격이 한국 밖 IP 를 막는다는 것이었다. 러너에서 curl 로 같은 호스트를 찔러보니 0.42초 만에 401 이 왔다. 호스트는 닿는다. 틀렸다.

두 번째 가설은 파이썬 기본 User-Agent 가 막힌다는 것이었다. 러너에서 파이썬으로 실제 요청을 보내니 1.09초에 200 과 XML 이 왔다. 이것도 틀렸다.

그 다음이 이상했다. 2분 뒤 같은 요청을 다시 보내니 이번엔 30초 타임아웃이 났다. 조사일이 있는 날짜든 없는 날짜든, 같은 날짜를 세 번 반복해도 전부 똑같이 타임아웃이었다. 날짜 문제가 아니라 실행 문제였다.

그래서 러너 IP 를 찍고 curl 과 파이썬을 같은 실행 안에서 번갈아 돌려봤다.

| 러너 IP | curl | 파이썬 |
|---|---|---|
| 172.212.165.72 | 200, 1.5초 | 200, 1.6초 |
| 172.182.211.25 | 연결 타임아웃 | 연결 타임아웃 |
| 48.217.107.114 | 연결 타임아웃 | 연결 타임아웃 |

한 실행 안에서는 curl 과 파이썬의 결과가 항상 같았고, 실행끼리는 달랐다. 클라이언트 문제가 아니라 IP 문제다. `apis.data.go.kr` 은 GitHub 러너가 받는 애저 IP 대역 일부에서 오는 TCP 연결을 거절하지 않고 그냥 버린다. 거절하면 즉시 오류가 나는데 버리니까 타임아웃이 난다. 러너 IP 는 실행마다 새로 받으므로, 같은 코드가 어떤 날은 되고 어떤 날은 안 된다. 여섯 번 시도해서 두 번 통했다.

고칠 수 없는 종류의 문제다. 상대 서버의 방화벽이고 우리 쪽에서 IP 를 고를 수 없다. 그래서 고치는 대신 설계를 바꿨다.

연결이 아예 닿지 않는 경우를 다른 실패와 구분해 `Unreachable` 로 따로 이름 붙였다. 수집을 시작하기 전에 한 번 찔러보고, 닿지 않으면 606회를 시도하지 않고 그냥 물러난다. 이때는 실패가 아니라 정상 종료다. 이어서 적재·매칭·점검·리포트는 이미 받아둔 조사분으로 그대로 돈다. 탐지용 요청의 대기 시간도 60초에서 20초로 줄였다. 막힌 IP 라면 오래 기다려도 오지 않는다.

대신 하루 한 번이던 크론을 세 번으로 늘렸다. 한 번에 통할 확률이 3분의 1이면 하루 세 번은 7할이고, 조사는 격주라 며칠 안에 잡으면 된다.

이렇게 하면 진짜 고장을 놓치지 않느냐는 문제가 남는다. 그건 점검이 잡는다. 조사 공백 항목이 마지막 조사일로부터 16일이 지나면 주의, 24일이 지나면 실패다. IP 가 계속 막혀 몇 주째 못 받고 있으면 그 항목에서 걸린다. 한 번 못 받은 것은 조용히 넘어가고, 계속 못 받는 것은 알림이 울린다. 둘을 구분한 것이 이 단계에서 배운 것이다.

## 2026-09-11 (금) 6단계, 알맹이 없는 커밋

어제 수동 실행 세 번이 봇 커밋 세 개를 남겼다. 들여다보니 파일 네 개에서 바뀐 것은 실행 시각 한 줄씩뿐이었다. 점검 시각, 매칭 실행 시각 같은 것들이다. 내용은 그대로였다. 크론을 하루 세 번으로 늘려둔 상태라, 두면 아무 일 없는 날에도 커밋이 하루 세 개씩 쌓인다.

점검표 파일 이름을 조사일로 바꿔서 이 문제를 막았다고 생각했는데 반만 막은 것이었다. 파일이 늘어나는 건 막았지만 같은 파일 안의 시각이 매번 바뀌었다.

시각을 하나하나 지우는 대신 커밋하는 조건을 바꿨다. 수집 단계가 이번에 새로 받은 조사일 수를 워크플로에 넘기고, 워크플로는 새 조사분을 받았거나, 리포트를 만들었거나, 무엇이든 실패했을 때만 커밋한다. 평범한 날에는 수집 0건, 리포트 없음으로 넘어가 커밋 단계를 건너뛰는 것을 로컬에서 확인했다.

## 2026-09-11 (금) 6단계, 슬랙 연결

웹훅을 만들어 `.env` 와 GitHub 시크릿에 넣었다. GitHub 에서 수동 실행을 돌려 "슬랙 전송 성공" 을 확인했다. 월요일 09:00 에 오는 메시지와 같은 경로다.

로컬에서 먼저 보낸 연결 시험은 실패했다. 이 맥의 파이썬이 인증서를 못 찾는 예전 그 문제였다. 수집 코드에는 우회를 넣어뒀는데 슬랙 알림 코드는 `urllib` 를 직접 불러 그 우회를 타지 않았다. 같은 우회를 알림에도 넣었고, CI 에서는 켜지지 않는 것도 같다.

붙여넣은 웹훅 주소 앞뒤에 따옴표나 공백이 붙어 있었다. `.env` 를 읽는 코드가 공백은 지웠지만 따옴표는 그대로 두어서, 그대로였다면 슬랙 주소가 깨졌을 것이다. 따옴표도 벗기게 고쳤다.

## 2026-09-11 (금) 리포트 문장 다듬기

리포트가 AI가 쓴 글처럼 읽힌다는 지적을 받았다. 한국어 AI 문체를 70여 가지 패턴으로 분류해둔 공개 규칙집(github.com/epoko77-ai/im-not-ai)을 기준으로 삼았다. 저장소의 스크립트는 돌리지 않고 규칙 문서만 읽어 적용했다.

리포트는 매주 코드가 새로 쓰므로 결과 파일이 아니라 문장을 만드는 코드(report.py, qa.py, notify.py)를 고쳤다. 원칙은 규칙집을 따랐다. 숫자와 상품명은 건드리지 않고, 빼기만 하고, 한다체는 그대로 둔다.

걸린 것은 이랬다. 순위표 20행 모두에 굵은 글씨가 있었다. 문장 속에 화살표가 있었다. `52g 을`, `json 에`처럼 조사를 띄어 썼다. "과자와 음료와 조미료"처럼 '와'가 겹쳤다. 6절은 줄바꿈 하나로 이어져 화면에서 한 덩어리로 보였다. 근사값 목록에는 메모 원문이 그대로 나와 "갈치(냉동, 100g)(같은 근사)"라는 문장이 찍혔다. 슬랙 메시지는 점검 결과를 `warn`이라고 영어 그대로 보냈고, 세 상품을 "1위"라는 이름표 하나에 붙였다.

고친 뒤 고치기 전 리포트와 숫자를 기계로 대조했다. 날짜 표기와 점검 시각을 빼면, 사라진 숫자는 일부러 지운 중복 "100g" 하나였다. 조사일 표식은 화면에 보이지 않는 주석으로 옮겼고, 같은 조사분 리포트를 두 번 만들지 않는 장치가 그 주석을 제대로 읽는 것도 확인했다.
